Your AI Says “Done.” Did the Action Actually Happen?

Learn how to build AI workflows that execute tool calls, verify outcomes and handle failures.

By Deepali Shinde · About 10 minutes

A customer asks: “Please cancel order 4821 before it ships.” The assistant replies, “Done,” but the order is still active. Generating a confirmation and changing an order are separate operations. Your application has to connect them.

This walkthrough is for software engineers adding tools to an AI assistant. You’ll learn how to execute a model’s request, check the result and explain rejection or uncertainty to the customer.

We will follow a successful cancellation first, then introduce the failures that shape the design. All customers, identifiers and traces are illustrative.

Connect the model to the application

Assume a signed-in customer and a rule that permits cancellation only before shipping. Three responsibilities connect the request to the outcome:

  • Model: interprets the request and proposes a cancellation.
  • Workflow controller: coordinates the application steps.
  • Order service: enforces the business rule and changes the stored order.

These roles can live in one application. The model proposes an action; application code checks whether it may run and records the result.

Follow the successful tool round trip

A tool is an operation the application makes available to a large language model (LLM). The model receives messages and a tool description, then can emit a structured request to use it. The controller dispatches that request to application code.

The next request may be ambiguous or fail a service check. Here is where the successful path needs to branch.

When the request cannot proceed

The successful path assumed one clearly identified, eligible order. If the customer says “cancel it” after discussing two orders, the controller needs a clarification before attempting either cancellation. The model can interpret the language and ask for the missing reference.

If the customer names another person’s order, the service must deny the action without disclosing that order’s details. The fix is an authorization check at the action boundary. Improving the prompt cannot grant or establish permission.

Treat the order ID as untrusted input, even when the model copied it correctly. Get the customer’s identity from the signed-in session and check which orders that customer may change.

Also keep the decisive eligibility check with the state transition. An order can move from “processing” to “shipped” between a lookup and a later cancellation attempt.

The service must check eligibility as part of the order update. This prevents a change between the earlier lookup and the write from bypassing the rule.

Clarification and rejection are valid outcomes. In both cases the application knows why no cancellation occurred. A lost service response introduces a different problem: the action may have happened without the controller knowing.

When the action happens but the response is lost

The order service commits the cancellation, but its response times out before the controller receives it. The order is cancelled; the controller’s last known status is still “submitted.” A timeout does not establish whether the action succeeded or failed.

The workflow’s record and the order service’s record have different jobs:

  • Workflow state: the chosen order, operation ID and last observed result.
  • Business state: the order’s actual status.
  • Conversation history: context for a follow-up such as “Did that go through?”

To recover, the controller needs evidence about the original attempt. A safe retry relies on idempotency: the service treats repeated attempts as one operation and avoids repeating its effect.

Save an operation ID before sending the request. Use that same ID to look up its result or retry the same intent under the service’s retry contract.

Reconcile the recorded result before issuing a new action. AWS’s guide to idempotent APIs explains this caller-provided identifier pattern and the service-side coordination it requires.

Production hardening: operation identity and retry limits

The identifier must represent one cancellation attempt, not just the order number: a different intent must not accidentally reuse it. The service must coordinate recording the identifier and the mutation, reject reuse with conflicting arguments, and define how long deduplication records remain valid.

If that protection has expired, reconcile or escalate instead of blindly retrying. A shared identifier alone does not make a side effect safe.

Until recovery establishes a result, record the outcome as unknown. When preparing the next model call, supply that recorded status as context. The model should not have to infer execution from the customer’s wording or from its own earlier response.

Make the response follow the observed outcome

The controller can now distinguish completion, rejection and an unknown outcome. A response gate is application logic that limits the reply to what the recorded result supports. For this action, it can produce a fixed status message:

A fixed template makes the status claim easy to enforce. For a more flexible reply, return the result to the model. Keep the status in a field rendered by application code, or check the generated claim against the result and fall back to a template if they disagree.

While streaming, emit progress separately: “Checking your order” may appear before completion. Release a cancellation confirmation only after the gate accepts the result.

Test the action and the answer

Run the request and check four facts: was the customer authorized, did the operation complete, is the order cancelled, and does the reply match? These are assertions, conditions that a test checks.

A trace is the recorded sequence of observable events: relevant inputs, proposed tool calls, validation decisions, service results, and state transitions. An evaluation runs a case and checks the behavior or outcome against explicit expectations. Anthropic’s agent-evaluation guide likewise distinguishes the transcript of a run from its final environment state.

For this small workflow, start with a few cases:

Case Evidence to check
Customer owns an eligible order Service records cancellation; response confirms the matching order
Customer names someone else’s order No unauthorized change or disclosure
“Cancel it” could refer to two orders Clarification before a cancellation attempt
Order ships before the action commits Service rejects the transition; response reflects rejection
Service response is lost Same operation is reconciled or retried safely; no unverified success claim

Keep the ordinary tests for permissions, state transitions, and retry behavior. Add cases that vary phrasing and conversation context to exercise model interpretation.

A model can help judge whether an explanation is clear, once its grades have been checked against human reviews. To check whether the order was cancelled, inspect the order state directly.

You do not need every run to use identical wording or an identical sequence of harmless reads. Define which ordering constraints matter, such as authorization before mutation, and allow valid alternatives elsewhere.

Find the boundary that failed

Suppose the service rejects cancellation, but the customer receives a success message. The response gate failed. The ownership check worked, so changing it would leave the bug in place.

A different trace demands a different fix:

  • Two plausible orders: if the model selected one without asking, inspect context and the clarification path.
  • Shipping started during the request: enforce eligibility at the mutation.
  • A retry repeated the effect: inspect operation identity and the service’s deduplication contract.

Save that trace as a regression test, then vary nearby inputs to check the fix. This ties each repair to the step that failed.

Decide how much planning the workflow needs

A fixed controller fits the cancellation task because the allowed steps are known. A task such as investigating an account may need the model to choose what to look up next. That changes the planning, while permission and result checks remain part of the application.

Approach and fitTrade-off and guardrail
Fixed workflow
Known actions with clear transitions		Easier to inspect and test; new branches require code. Let the model interpret language and ask clarifying questions within those transitions.
Bounded model-directed loop
Investigations whose next read depends on findings		More flexible, but variable latency, cost and paths. Limit available tools, turns and time; enforce authorization on every action and stop when the budget expires.
Hybrid
Flexible investigation followed by a constrained action		Useful when discovery is open-ended but mutation has strict rules. More handoff state to maintain; validate the proposed action again at the execution boundary.

For an initial cancellation feature, begin with the fixed path. Add a planning loop only when representative requests show that the predefined flow cannot handle useful variations. More autonomy creates more execution paths to observe and evaluate.

Apply the pattern to another action

Try the same design on a refund or booking. First identify the service that owns the change and the result it can report. Then decide which replies are valid for completion, rejection and uncertainty.

Some actions need extra confirmation or finish asynchronously. Model those states explicitly, and test what the customer sees while work is pending. Extend the workflow only as far as you can explain and verify its outcomes.

The customer, order number, and execution paths in this article are illustrative. The interface is conceptual; this article does not provide a complete backend implementation.
